# AutiConnect database design

This is a logical schema. M1 introduces the identity and consent foundation. Later milestones add their own entities and migration tests.

## Entities and relationships

All account-owned rows use a UUID identity or composite primary key and a non-null `user_id`. Use UTC `timestamptz` fields and distinguish the time an event occurred, became available to the application and was persisted when they differ.

| Entity | Key fields and relationships | Lifecycle |
| --- | --- | --- |
| `profiles` | `user_id` references `auth.users`. Allowlisted, user-entered profile fields and timestamps. | Editable by the account owner. |
| `consent_events` | Owner, purpose, decision, notice version, effective timestamp and idempotency key. | Append-only while the account exists. Resolve latest state per purpose, with absence treated as disabled. |
| `conversations`, `messages` | Conversation owner, session timestamps and expiry. Each message records its owner, conversation, author role and creation time. | Bounded working window. Apply an explicit retention policy to any stored history or source retained for review. |
| `memories` | Owner, kind, scope, normalised claim key, current confirmed revision pointer and review status. | Retire or purge via user control. Working context stays in the conversation. |
| `memory_revisions`, `memory_sources` | Revision value, schema and extraction version, review state, validity dates and correction lineage. Source edges record message or direct user action, capture time and source kind for that revision. | Preserve review lineage while sources and revisions are eligible to retain. A deleted source invalidates dependent claims that lack sufficient remaining evidence. |
| `memory_embeddings` | Owner, revision, encoder and encoder revision plus `vector(d)` where `d` is chosen for the first model. Unique per revision and encoder. | Populate for confirmed revisions. Remove or exclude embeddings when revisions become ineligible. |
| `explicit_preferences`, `goals` | Owner, scope, typed value and status. Optional source revision and user action reference. Preferences enforce uniqueness for each active scope and setting. | User edits are immediately authoritative and changes are attributable. Resolve deletion choices for linked values without inferring a new preference. |
| `interaction_events` | Owner, stable event ID, event type, target and version, session, pre-choice context, availability timestamps and consent reference. Structured allowlisted payload only. | Repeat requests return the existing result for the same event ID. Honour withdrawal and deletion. |
| `training_observations` | Owner, source event, target, versioned feature payload and label, eligibility and feature/label availability times. | One logical observation per owner, event and target. Feature schema versions identify reproducible transformations and do not create extra logical labels. |
| `dataset_manifests` | Dataset ID, source kind, seed/config hash for synthetic datasets, split rule, feature schema version and checksum. Private owner-scoped membership associates account observations with a split and run. | Reproducible fold membership while data is eligible. Rebuild affected manifests after deletion and remove identifying membership. |
| `model_runs`, `model_versions` | Run, lifecycle state, target, dataset reference, split-specific scores, parent, artifact path, dependency versions and checksum. | Account versions have an owner. Keep shared synthetic catalog records in separate read-only published surfaces. State transitions record acceptance, rejection, retirement and invalidation. |
| `active_preference_models` | Owner and target key, current version plus data revision used for concurrency control. | One active pointer per account and target. Change it transactionally for promotion, rollback or deletion. |
| `predictions`, `prediction_evidence` | Owner, target, model version, context scope, generated and expiry times, class scores or abstention reason, and owner-scoped links to eligible evidence. | Keep only as needed for transparency and expiry. Invalidate affected entries when a version or source becomes ineligible. |
| `learning_jobs`, `user_actions` | Owner, job kind and retry state or action type and time. Use stable operation IDs for extraction, review, training and deletion. | Keep only minimal operational metadata and attributable user actions. Purge payloads and delete account-linked metadata on account deletion. |

## Constraints and access control

- Enforce same-owner references using composite foreign keys such as `(user_id, conversation_id)` to `conversations(user_id, id)`. Apply the pattern to source edges, evidence, jobs, versions and pointers. Model inheritance from a shared synthetic starter uses a separate catalog reference.
- Enable RLS on account tables and restrict grants to required operations. Owner read/write policies compare `user_id` to `auth.uid()` and validate ownership of inserted and updated rows. Expose user-editable data through allowed operations and keep internal tables or write paths private. Derive caller scope inside any owner-facing RPC. Prefer invoker privileges and explicitly test view and RPC access. [Supabase row-level security](https://supabase.com/docs/guides/database/postgres/row-level-security)
- Index owner and common access keys. Starting indexes cover conversation messages by time, memory rows by owner, review status and scope, observations by owner, target and availability, and run history by owner and creation time.
- Use unique keys for interaction ingestion and extraction retries. An extraction deduplication key includes source identity, source revision and extraction version. Unique confirmed claim keys apply only where the domain expects one current value in a scope. Episodes can have multiple distinct occurrences. Semantic similarity may propose a match and cannot silently replace a confirmed value.
- Start with exact cosine ranking over a small eligible subset using pgvector. Require the owner, supported encoder revision, review status and validity in the same query. Measure recall and latency on selective owner filters before adopting an approximate index. Re-embed eligible revisions when switching encoders and query only matching vectors during cutover. [pgvector indexing and filtering](https://github.com/pgvector/pgvector)
- Store model files in private storage, identified by immutable paths and checksums. Resolve artifact access through the owner-scoped version record. The application loads only trusted artifacts created by its own jobs.

## Activation, rollback and deletion

**Activation.** Each run stores its expected parent, starting training-data revision, exact eligible update membership and evaluation slice. Increment the training-data revision when eligible observations or consent change. Stage the artifact before publishing. Atomically validate the current revision, consent and parent before moving the active pointer. A run that loses this check must replan from current state. Use membership and parent lineage to identify what each version has already consumed. Rolled-back versions may replay eligible observations from the appropriate lineage checkpoint without applying a sample twice in one model history.

**Rollback.** Select a compatible previously evaluated version whose complete lineage remains eligible, verify its artifact and record the pointer transition. Retain historical run metadata as permitted. Use the default when no such version exists.

**Deletion.** Remove the requested row or content and dependent copies from retrievable state at the start of the operation. For memory deletion, purge its revisions, embeddings and derivation evidence, and prevent retry of already processed source material from recreating the deleted memory. Explain the separate controls for deleting a retained conversation and any independently saved preference or goal. For training deletion, invalidate affected features, manifests, predictions, result slices and model versions, including descendants and versions evaluated on the deleted row. Stop serving invalid versions and clear the relevant pointer in the same transaction. Schedule artifact cleanup and rebuild from an eligible checkpoint or the clean synthetic starter. A rebuild independently passes the evaluation and activation gate before serving.

**Retention.** Define user-visible retention periods and backup expiry before storing approved personal data. A minimal deletion marker can retain a non-content request or source identifier only for the period needed to prevent job replays. During restore, reapply required deletions before enabling access. When training consent is withdrawn, immediately stop intake, training and use of affected personal predictions. Offer the training-history deletion path. Apply equivalent protections to memory retrieval consent and explain retained records in the UI.
